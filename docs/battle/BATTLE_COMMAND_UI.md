# Battle command windows, status panes and the fused MetaSlug

Decoded 2026-10-02 against the retail cartridge for issues #51, #52 and #64.
Every value cites a routine in `reference/ps4disasm/ps4.asm` (retail `loc_`
addresses, per [BATTLE_GEOMETRY.md](BATTLE_GEOMETRY.md)) and the oracle frame it
was read from. Five new pairs in `tools/certify.py` hold the result at
`rmse=0.000000`; the mid-round attack (#52) is described separately, see
[Mid-round attack](#mid-round-attack-52).

## The layout authority

The decoded files under `oracle/layouts/` (local inputs, regenerated by the
oracle) are the authority for the battle screen's plane-A geometry;
[BATTLE_GEOMETRY.md](BATTLE_GEOMETRY.md) is context, and a disagreement is
resolved in favour of the decoded layout.

`rust/psiv-godot/src/battle/chrome.rs` and `layout.rs` render the retail window
atlas, menu font, command cursor, the 36x6 status window with its decoded
separator holes, the HP/TP labels and the decoded number glyph run.
`rust/psiv-godot/src/battle/ui/mod.rs` holds the enemy-name, command, victory,
status, message and enemy-anchor constants; its oracle-gated tests read the
layout files when they are present and assert the decoded rectangles, text
origins, tile-run spans and visible sprite coordinates.

`PSIV_DEBUG_BATTLE=0x88` is the command-idle fixture: Chaz, Alys and Hahn with
25/10, 53/40 and 21/25 HP/TP against two Zoran Bults at the decoded body
anchors `(88,72)` and `(184,72)`. It is a capture selector, not a formation id.
`oracle/layouts/battle_command_idle.json` has no visible sprite-table entries
for this fixture, so its position proof is the decoded body anchor plus the
overlay placement metadata.

Enemy bodies are built from the pack: the extractor decodes
`EnemySpriteMappingsOffs`, both retail sequence encodings, the Art #2 source
patterns, the Art #3 destination tiles and the body-relative placements, and
the renderer rebuilds each body with the replacement tiles at the retail
`duration + 1` cadence ([enemy art](#the-art-comes-from-the-pack)).

## The per-character command strip (#51)

`Battle_OpenCharComd` (`ps4.asm:2085`) opens a 16x4-cell window and writes five
2x2 icons into it; `Battle_CharCommand` (`ps4.asm:2192`) moves a sprite cursor.

| fact | value | source |
| --- | --- | --- |
| window | 16x4 cells at plane row 17, column 3, 15, 9, 9, 15 by `Battle_Total_Comd_Input` (fighter slot - 1) | `loc_17A4` `ps4.asm:2397-2398`; plane dump of frame 25134 |
| icons | window-local columns 1, 4, 7, 10, 13 of row 1; ATTACK only when a hand holds a weapon, TECH/SKILL/ITEM only when their list is non-empty, DEFEND always | `ps4.asm:2108-2160` |
| icon words | `BattleTiles_*Icon` `$E15E..$E17A` (CRAM line 3, priority) | `ps4.asm:11258` |
| cursor | Left/Right through `Battle_UpdateCursor` (`ps4.asm:70646`), wrapping over five icons; Up/Down are not tested | `ps4.asm:2192-2212` |
| cursor sprite | 2x2 at x = first icon x + 24 * index, y 156, tile `$17C` then `$180`, six ticks each | `ps4.asm:70465`, `70494`; SAT of frames 25080-25160 |
| cursor lag | the VDP reads the sprite table a frame after the object writes it, so the frame on screen is the one the clock had a tick ago | video 25134 shows RAM state 25133 |
| other bodies | the plane clears the party rows as the window opens and draws only the acting body | `loc_E4C` (`ps4.asm:1509`), `loc_E64` (`ps4.asm:1525`), `loc_EB6` (`ps4.asm:1552`) |

Cancel from a list window reopens the strip on the icon that opened it
(`Battle_BackFromTechs`, `ps4.asm:2792-2804`) and clears that member's command byte.

## The technique, skill and item windows (#51)

`Battle_TechWindow` (`ps4.asm:2593`), `Battle_SkillWindow` (`ps4.asm:2933`) and
`Battle_ItemWindow` (`ps4.asm:3325`) show **four rows a page**.

- Window at plane row 12, columns 4, 16, 10, 10, 16 (`loc_19D0`, `loc_1D5E`,
  `loc_2154`); 12 (tech), 16 (skill) or 14 (item) cells wide, 9 high.
- Entry `k` is at row `13 + 2k`: cursor tile `$6E7`/`$6E8` at column 1, name at
  column 3, the number at columns 8-10 (tech cost) or 11-13 with window tile
  `$6FF` over the hundreds cell (skill uses). A disabled entry sets `$C000`
  (CRAM line 2) and ignores accept.
- `Battle_UpdateRedCursor2` (`ps4.asm:1572`): Up/Down wrap **inside the page**,
  whether or not the row holds an entry. Right flips to the next page only when
  the page's top-right corner holds the arrow word `$6EE6`, Left likewise with
  `$66E6` at the top-left (`ps4.asm:2603-2608`); a flip returns before the
  Cancel and accept tests.
- The red cursor blinks: `$FFFF41D2` counts down, `$FFFF41D4` is the phase;
  25 frames red, 15 blue, a held button or an accept press forces red
  (`ps4.asm:1590-1620`). The runtime keeps both words (`session/battle/blink.rs`).

Receipt: tape 32 (`oracle/tapes/32_battle_command_windows.tape`, frame 25134
the strip with the cursor on TECH, frame 25400 the technique window: SANER 6,
SHIFT 7, FOI 3).

### Each member's cursors are remembered

`Battle_Char_Comd_Index`, `Battle_Tech_Index` and `Battle_Skill_Index` are one
word per party slot (`ps4.asm:2195`, `2598`, `2938`), and nothing clears them
during a battle, so a member's strip and lists reopen where that member left
them, an empty row included. `Battle_Item_Index` is per member too, and
`loc_5BAE` clears its five words at each round's end (`ps4.asm:8422-8425`).
`CursorMemory` (`menu/commands.rs`) holds the four, the battle mode carries it
between windows and clears the item words where it clears the command table.
Test: `each_member_s_strip_and_list_cursors_reopen_where_they_left_them`.

### The windows grow open

`Battle_CreateWindow` (`ps4.asm:1657`) adds two cells to `$FFFF418C` each
frame and draws an empty window that wide, shifted right by
`(d1 - width) & ~1` bytes (two a cell) so it grows from the centre of where the
full window goes. Once the width reaches the window's `d1` it draws the whole
window, contents and all, and returns past the caller's `rts`, which is the
frame the routine moves on to the window's input routine. Until then no
button is read, the red cursor's timers do not run, and the strip's cursor
object does not exist (`move.w #4,(Command_Cursor).w` comes after,
`ps4.asm:2175`). A list opening clears the strip's cursor as it starts
(`clr.w (a4)`, `ps4.asm:2339`).

| window | `d1` | frames | source |
| --- | --- | --- | --- |
| strip | `$10` | 8 (2-14, then whole) | `loc_1566`, `ps4.asm:2170` |
| technique | `$C` | 6 | `loc_18DA`, `ps4.asm:2489`; next page `Battle_TechNextWin` |
| skill | `$F` | 8 (14 is left-aligned, then whole) | `loc_1C66`, `ps4.asm:2830`; `Battle_SkillNextWin` |
| item | `$E` | 7 | `loc_2036`, `ps4.asm:3186`; `Battle_ItemNextWin` |

Tape 32: TECH accepted at f25165, `Battle_Routine_2` `$8007` from f25166 to
f25170, `Battle_TechWindow` from f25172; the video shows boxes of 2, 4, 6, 8
and 10 cells at f25167-f25171, the list at f25172 and the red cursor at
f25173. The strip from COMD: boxes of 2-14 cells at f25008-f25014, the icons at
f25015 and the cursor at f25016.

`CommandsMenu` holds the width while a window grows and reads no button; the
view's `growing` carries it, and the stage draws an empty window at that width
in place of the strip or list. Test:
`the_strip_and_the_technique_window_grow_before_they_read_a_button`.

The frame a list is drawn whole is still `Battle_CreateWindow`'s: the list
routine, whose `Battle_UpdateRedCursor2` (`ps4.asm:1572`) writes the selected
row's red or blue tile and runs the blink timers, first runs the next frame
(tape 32: the list at f25172, the red cursor at f25173). So the whole frame's
row is blue whatever the blink last showed, and the timers stay paused
through it; the same holds for a next page's window. `CommandsMenu::list_cursor_shown`
carries that to the view's `cursor_red`. Tests:
`a_list_drawn_whole_shows_its_cursor_only_from_the_next_frame` (TECH, SKILL,
ITEM and a next page) and
`the_skill_and_item_windows_show_no_red_cursor_until_their_routine_runs`.

### Not modelled, named

- The closing side: `Battle_DestroyWindow` (`ps4.asm:1678`) shrinks a window
  the same way when the main options give way to the strip (f25003-f25005 in
  tape 32), when a list closes on a choice or a cancel, and on a previous-page
  flip (`Battle_TechPrevWin`). The port removes those windows at once.
- The frames between COMD and the strip's growth: the main options' shrink,
  `Battle_ProcessCOMD`'s frame and `Battle_OpenCharComd`'s setup frame, which
  in tape 32 also runs long enough to drop a video frame. The port's strip
  starts growing the frame after COMD, so it is whole five frames earlier than
  the cartridge's.
- The skill and item windows are decoded from their routines and drawn by the
  same code, but no oracle frame certifies them.
- Target selection is the cartridge's sprite cursor over the enemies or party
  (`Battle_PickTargetEnemy`, `ps4.asm:1216`); the port keeps its one-list page.

A sealed member **can** choose a technique, as in the cartridge: the window
refuses an entry on TP alone (`Battle_FillTechList` sets the sign bit,
`ps4.asm:1721`; `Battle_TechWindow` ignores it, `ps4.asm:2628`), and the cast
is paid and wasted (`CharTech_CheckTPCost` `ps4.asm:14211`, `CharTech_Cast`
`ps4.asm:14256`; the engine's `TechniqueRejected(Sealed)` after the paid
`TechniqueUsed`). One rule decides what each window enables, and the menu
view reports that same rule: `CommandsMenu::technique_enabled`,
`skill_enabled` and `item_enabled` draw the rows, and `TechniqueEntry.available`
and `SkillEntry.available` are the same answers, so the view also offers a
sealed member's technique. A caller that wants to avoid the wasted turn reads
the seal from the actor's `PartyStatus.status` (the campaign planner does,
`Planner::in_stock`). Tests: the pad-only
`a_sealed_member_may_choose_a_technique_and_the_cast_is_wasted`, and
`a_sealed_member_picks_a_technique_the_view_agrees_and_the_cast_is_paid_and_wasted`
with its unsealed control (`commands_tests.rs`).

## Status panes (#64)

`Battle_DrawCommandIcons` (`ps4.asm:11056`) runs every frame and decides each
pane's icon and ink from the member's status byte and command byte
(`Battle_Command_Data`, four bytes a member):

| status | icon | CRAM line of the pane's text |
| --- | --- | --- |
| `$44` dead | 8 | 2 |
| `$08`/`$20` asleep | 7 (paralysis `$02` outranks it with 6) | 1 |
| `$02` paralyzed | 6 | 1 |
| `$01` poisoned | the command icon | 0 |
| tech sealed `$10` | **nothing**: the routine never tests it | 3 |

The icon replaces the command byte, and a status icon whose status has gone
reads back as no command. Icons are always drawn on CRAM line 3; only the name,
HP/TP labels and numbers change ink: index 15 of line 0/1/2/3 is `$02CE`,
`$0CC4`, `$062E`, `$0EEE` (`loc_7654`, `ps4.asm:11227-11239`). The command byte is 0
none, 1-5 attack, tech, skill, item, defend; 9 an empty seat. The runtime owns
the decision (`session/battle/panes.rs`); a round's end clears the table
(`loc_5BAE`, `ps4.asm:8419`).

Receipts, tape 32 at frame 25000 with `Character_Stats` status patched one
frame earlier: Chaz asleep `$08`, Alys paralyzed `$02`, Hahn sealed `$10`
(`battle-status`); Chaz poisoned `$01`, Alys dead `$04`, Hahn asleep and sealed
`$18` (`battle-status-2`).

## The fused MetaSlug (#64)

Fusion (`docs/battle/ENEMY_FUSION.md`) rebuilds the enemy side from
`loc_1A2F4`: one enemy, id 36, **position `$14`**. The runtime event now
carries the position and the battle view's `EnemyStatus` the enemy id and
position; the shell rebuilds slot 1 with the MetaSlug art, palette, overlay
clock and damage column exactly as a formation builds them. Receipt: tape 33
(`oracle/tapes/33_zol_fusion_metaslug.tape`, formation `$D2` forced with the
three patches in `tools/certify.py`'s `TAPE_33`), frame 25560, options back
over the MetaSlug. The party defends in the clone's round; the slugs' turn is
Fusion whatever it rolls. The two pieces sliding together and growing
(`BattleObj_Fusion`, `ps4.asm:35675`) are drawn frame for frame
([`ENEMY_FUSION.md`](ENEMY_FUSION.md#the-slide-and-the-growth-64)).

## Mid-round attack (#52)

The runtime owns each live attack object's identity and absolute age in
`BattleView.attacks`: dispatch starts at age zero and subsequent game frames
advance it. Reading or applying the same view cannot advance an object.
Godot advances the idle overlay art before applying the frame's runtime view,
then draws the attack's mapping and motion at the supplied age. The transition
is covered by `an_attack_animation_cue_rides_the_first_frame_of_its_beat` and
the pack-independent `battle::attacks` tests.

The retail order is `Battle_UpdateFighters`, followed by the objects' first
run, which draws mapping zero (`GameMode_Battle`, `ps4.asm:947-966`). Tape 34
shows Zoran attack sprites for sixteen frames, 25368-25383, with two frames per
mapping. Its object's coordinates are relative to the fighter's centre
(`loc_12618`), rather than the body's right edge. During the strike the first
overlay piece is frozen at frame 2/timer 6; its VRAM replacement is also read
by the attack mapping. `EnemyAttack_ZoranBult` writes line 2 colours 10-12,
while the object's init selects that line. The extractor pins the USA routine,
init and freeze signatures before emitting those tiles and palette changes.

The strike fixture also supplies the displaced target's horizontal pivot and
the frozen overlay pose through the runtime view. The full windup, target
reaction and overlay release are a separate gap:
[#421](https://github.com/TusanHomichi/PSIV/issues/421). A strike capture does
not certify that complete sequence or a connected campaign route.

## The art comes from the pack

The icon and cursor tiles are the two Nemesis streams `loc_7382` loads
(`ps4.asm:10978-10986`): 30 tiles at ROM `$27D860` to VRAM tile `$15E`, 8 at `$27DA70`
to `$17C`. `loc_7634` copies 15 words from ROM `$76A4` (`loc_76A4`,
`ps4.asm:11213-11250`) into CRAM line 3, indices 1-15. The extractor writes
both the CRAM-index rows and that palette into `battle/art/command_ui.json`,
with a manifest `command_ui` entry and `command_ui_tiles` census. `psiv-data`
requires all 38 VRAM tiles `$15E..$183` and the 15 valid palette words;
`rust/psiv-godot/src/battle/tiles.rs` draws from them. For a local native run,
set `PSIV_RUNTIME_PACK` to the absolute path of a real pack copy; `Field::ready`
uses that path for every loader. It checks the typed file while configuring
battle, then exits with a rebuild error if it is missing or corrupt. No
ROM-derived pixels or palette are
committed. `command_art_matches_the_oracle_vram` (Rust) and
`test_command_ui_art_matches_oracle_vram_and_cram` (Python) compare every tile
and palette word to `oracle/states/battle_command_idle_vdp_25000.json`;
`public_load_requires_every_vram_tile_and_the_palette` rejects incomplete
synthetic packs through the public loader.

The damage-number tiles come from the pack the same way. The battle setup
decompresses one Nemesis stream, 28 tiles at ROM `$27D778`, to VRAM `$BC80`
(tile `$5E4`, `ps4.asm:10007-10009`). The extractor writes their CRAM-index rows
to `battle/art/damage_digits.json`, with a manifest `damage_digits` entry and
`damage_digit_tiles` census; `psiv-data`'s `DamageDigitArt` requires all 28
tiles `$5E4..$5FF`, and `rust/psiv-godot/src/battle/chrome.rs` builds the
damage-number words from them (index 14 the window fill, 15 the white ink, 2
the grey rule). Without the file the battle chrome does not build and the error
names it. `test_damage_digit_art_matches_oracle_vram` compares every tile to the
same oracle state. No tile is written as pixels in the tree:
`tools/check_rom_tables.py` fails one (#149).

## Pins

Clone tick `t` pairs with oracle frame `24800 + t` for the Academy fixtures
(`PSIV_DEBUG_BATTLE_WINDOW`): the battle starts at tick 30 with the overlay
clock seeded. The enemy's overlay clock is the cartridge's `Enemy_Sprites`
`(frame, timer)` words solved for the phase `E` (`E = 536` at 25377, `F -
24841` after the strip opens, one update skipped as it opens); a shot shows the
state after the tick's drive, the video frame the RAM of the frame before, so
`PSIV_DEBUG_BATTLE_PHASE = E(F) - 1 - (t - 29)`. The strip's cursor pins an
age (`age=7`), the technique window's blink pins `$FFFF41D2/4` (`blink=14/1`),
and the status pairs read `$FFFF41D2/4 = 17/0` at frame 25000 (`blink=3/1`).
