# Feature map

One index for the native game: per player-facing feature, the paths that own
it, how a player reaches it, the focused check that proves it and the ledger
that records its evidence. The [project overview](../README.md) says how far the
campaign has got; this map says where each feature lives.

**The map is checked, not trusted.**
`PYTHONPATH=. python3 -m unittest tests.test_feature_map -v` parses these
tables and fails when an owning path, a test target, a Python module or a
ledger link stops resolving, and when a new
`rust/psiv-runtime/tests/*.rs` target or a new `tools/native/` driver has no
row. Add the row in the change that adds the target, and point the same check
at a rotted copy to see it fail (`tests/test_feature_map.py`, `NegativeControl`).

How to read a row:

- **Owning paths** are repository-relative and current: the Rust module(s) under
  `rust/`, the Godot shell file(s) under `rust/psiv-godot/src/` or `godot/`, the
  extractor module(s) under `psiv_tools/`, and the `tools/native/` driver that
  exercises the feature as a player where one exists. A driver proves the
  interaction path, not the state; the focused test proves the state.
- **Player reach** is the ordinary-input route in the native build, named the
  way a player meets it. A `PSIV_DEBUG_*` fixture is not player reach.
- **Focused test** is the smallest useful existing check, in
  [the workflow's verification table](AGENT_WORKFLOW.md#find-the-smallest-useful-verification)
  form: a Rust integration target runs as
  `CARGO_BUILD_JOBS=1 cargo test --manifest-path rust/Cargo.toml -p <crate> --test <target> -- --test-threads=1`,
  a shell's own units as
  `cargo test --manifest-path rust/Cargo.toml -p psiv-godot --lib <module>:: -- --test-threads=1`,
  and a Python module as `PYTHONPATH=. python3 -m unittest tests.test_x`. These
  are state checks: a Godot-shell row's command covers that shell's units, and
  the visual half stays with the row's drivers and the ledger's captures. Most
  `psiv-runtime` and `psiv-data` targets and several Python modules read the
  local pack, so without it they either skip (the case returns early) or fail on
  the missing manifest; prepare the inputs first
  ([setup guide](DEVELOPMENT.md#prepare-the-local-pack)), and read the run's own
  output rather than its exit status. `python3 tools/gate.py` runs the whole set.
- **Ledger** is the document that owns the retail citations and the recorded
  evidence. A passing test does not certify a campaign route, and a scene
  transcription does not certify play.

## Gaps this map does not close

- Rows name the smallest useful check, not full coverage. A mapped target that
  skips without the local pack proves nothing about this build until the pack is
  prepared; the [gate](DEVELOPMENT.md#gate-and-coverage) reports that distinction.
- Research-only features (unimplemented abilities, later-campaign scenes) have
  no row here: they have no owner, no native path and no passing focused test.
  The [roadmap](ROADMAP.md) tracks them.
- Campaign progress is not a column. Each ledger under `campaign/` owns the
  connected-route evidence, and [the playability ledger](campaign/NATIVE_PLAYABILITY.md)
  is the entry point.
